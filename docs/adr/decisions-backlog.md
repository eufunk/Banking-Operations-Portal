# Architekturentscheidungen (Backlog)

Diese Liste sammelt die wichtigsten Entscheidungen, die wir im Projektverlauf treffen. Sobald wir eine Entscheidung tatsächlich umsetzen, wird sie als eigenes ADR-Dokument (`docs/adr/0001-....md` usw., nach dem gängigen ADR-Format: Kontext, Entscheidung, Konsequenzen) ausformuliert. Hier zunächst nur die Kurzfassung zur Orientierung.

| # | Entscheidung | Kurzbegründung |
|---|---|---|
| 1 | **Modular Monolith statt Microservices** | Passt zum Projektumfang, vermeidet Infrastruktur-Overhead, entspricht typischen Einstiegs-/Mittelstands-Enterprise-Setups im Bankenumfeld |
| 2 | **Blazor Web spricht Api ausschließlich über REST/HTTP an**, kein In-Process-Zugriff auf Application | Zeigt echtes API-Design, hält UI/Backend sauber getrennt, API bleibt für weitere Clients wiederverwendbar |
| 3 | **EF Core, Code-First mit Migrations** | Standard in .NET-Enterprise-Umgebungen, gute Interviewrelevanz, Migrations dokumentieren Schema-Historie |
| 4 | **Kein generisches Repository<T> über EF Core** | `DbContext` ist bereits Unit of Work + Repository; ein zusätzliches generisches Repository verdeckt EF-Core-Fähigkeiten (Includes, Projektionen) ohne echten Mehrwert – stattdessen fokussierte, use-case-orientierte Repository-Interfaces pro Aggregat |
| 5 | **DTOs statt Domain-Objekte über die API**, Mapping explizit (Mapster oder manuelles Mapping) | Verhindert Over-Posting/Under-Posting, entkoppelt API-Vertrag von internem Domain-Modell |
| 6 | **Validierung mit FluentValidation in der Application-Schicht** | Zentral, testbar, unabhängig von Controller/UI |
| 7 | **Strukturierte Fehlerbehandlung via ProblemDetails (RFC 7807)** + globale Exception-Middleware | Konsistente, maschinenlesbare Fehlerantworten, kein Stacktrace-Leak |
| 8 | **Authentifizierung über Azure AD/Entra ID (OpenID Connect)** statt eigenem Identitätssystem | Realistisch für Enterprise/Bankenumfeld, kein Passwort-Handling in eigener Verantwortung |
| 9 | **SAP-Anbindung über Interface-Abstraktion (Anti-Corruption Layer)** | Fachliche Logik bleibt unabhängig von SAP-RFC-Details, austauschbar/mockbar für Tests |
| 10 | **Secrets ausschließlich über Key Vault + Managed Identity** | Keine Secrets im Repo, keine manuelle Credential-Verteilung |
| 11 | **API-Versionierung über URL-Segment (`/api/v1/...`)** | Explizit, leicht verständlich, gut sichtbar in Doku/Tests |
| 12 | **Logging mit Serilog, strukturiert, Sink nach Application Insights** | Korrelation über mehrere Schichten/Requests hinweg möglich |
| 13 | **Payment-Status als explizite State Machine**, nicht als freies Enum-Feld | Verhindert ungültige Statusübergänge (z. B. `Executed` → `Draft`), zentrale Stelle für Transitions-Regeln |
| 14 | **Audit-Logging via EF Core `SaveChanges`-Interceptor**, nicht manuell pro Use Case | Konsistent, kann nicht vergessen werden, ein zentraler Ort für Nachvollziehbarkeit |
| 15 | **`Microsoft.AspNetCore.Components.QuickGrid` statt Telerik UI for Blazor** (umgesetzt) | Telerik UI for Blazor ist kommerziell und erfordert eine aktive Lizenz + privaten NuGet-Feed-Zugang; die Trial-Aktivierung scheiterte an einer geforderten Geschäfts-E-Mail-Adresse. Ein Portfolio-Projekt sollte nicht von einer befristeten/unsicher verfügbaren kommerziellen Lizenz abhängen. QuickGrid ist offiziell, kostenlos und deckt Server-side Paging/Sorting/Filtering vollständig ab; die Grid-Komponenten sind so gekapselt, dass Telerik bei Bedarf später nachgerüstet werden könnte. |
| 16 | **Lokal simulierte Authentifizierung (Cookie + Demo-Nutzer) statt sofortigem Azure AD/Entra ID** (umgesetzt, ersetzt #8 vorläufig) | Kein Azure-AD-Tenant/App-Registrierung vorhanden. Rollenmodell (BankEmployee/OperationsManager/Administrator) und `[Authorize(Roles=...)]`-Policies sind bereits so gebaut, dass nur der Token-Aussteller ausgetauscht werden müsste - eine spätere Migration auf echtes Entra ID ändert nichts an der Autorisierungslogik selbst. |
| 17 | **Azure Key Vault/App Configuration im Code vorbereitet, aber inaktiv** (umgesetzt) | Keine Azure-Subscription vorhanden - Managed Identity lässt sich ohnehin nicht lokal testen (funktioniert nur für tatsächlich in Azure gehostete Ressourcen). `Program.cs` prüft `AzureAppConfiguration:Endpoint`/`KeyVault:Uri` und überspringt die entsprechende Registrierung vollständig, wenn nicht konfiguriert - lokal laufen wir mit appsettings.json + User Secrets + Environment Variables (siehe [configuration.md](../architecture/configuration.md)). |
| 18 | **OpenTelemetry SDK statt klassischem Application Insights SDK; Konsolen-Exporter lokal, Azure-Monitor-Exporter nur bei konfigurierter Connection String** (umgesetzt, ersetzt #12 vorläufig) | Das klassische `Microsoft.ApplicationInsights`-SDK gilt bei Microsoft selbst als Legacy-Pfad zugunsten von OpenTelemetry (herstellerneutraler Industriestandard, gleiches Instrumentierungsmodell für Traces/Metriken/Logs über AWS/GCP/Azure hinweg - bessere Interview-Relevanz als ein Azure-spezifisches SDK). Trace-Correlation (`ActivitySource`/`Activity`) und Custom Metrics (`Meter`/`Counter`/`Histogram`) sind reine .NET-Bordmittel (`System.Diagnostics`), keine Zusatzpakete nötig - genauso wie `ActivityTrackingOptions` für automatische TraceId/SpanId-Anreicherung der Logs anstelle von Serilog. Anders als bei Key Vault/App Configuration lässt sich diese Kette (Request → Payment Application Service → SQL → geplant SAP) lokal vollständig ohne Azure-Subscription verifizieren, weil der Konsolen-Exporter immer aktiv ist; der Azure-Monitor-Exporter wird nur zusätzlich aktiviert, wenn `ApplicationInsights:ConnectionString` gesetzt ist (dasselbe Gate-Muster wie bei #17). Details: [observability.md](../architecture/observability.md). |

| 19 | **SAP-Anbindung als HttpClient-basierter Adapter statt SAP .NET Connector (NCo)/direktem RFC; MockSapCustomerService als lokaler Standard** (umgesetzt, konkretisiert #9) | Der SAP .NET Connector ist eine proprietäre, nur mit aktivem SAP-Vertrag/-Account beziehbare Bibliothek - kein NuGet-Paket, keine Testmöglichkeit ohne echtes SAP-System. `SapRfcCustomerService` bildet stattdessen das in der Praxis verbreitete Muster "RFC-fähiges SAP-Gateway/OData-Service" über einen ganz normalen `HttpClient` ab (mit Timeout/Retry/Circuit-Breaker über `Microsoft.Extensions.Http.Resilience`) - architektonisch identisch zur Anti-Corruption-Layer-Idee aus ADR #9 (Domain/Application kennen nur `ISapCustomerService`), aber tatsächlich kompilier- und lokal testbar. Ohne konfigurierte `Sap:BaseUrl` (Standardfall - kein SAP-System vorhanden) registriert `Banking.Infrastructure` stattdessen `MockSapCustomerService` mit deterministischen Fake-Daten - dasselbe Gate-Muster wie bei #17/#18. Der Graceful-Degradation-Pfad (SAP nicht erreichbar → lokale Daten trotzdem liefern, `sapAvailable: false`) wurde lokal sowohl gegen den Mock als auch gegen die echte HttpClient-Implementierung (gegen einen absichtlich nicht erreichbaren Port) verifiziert. Details: [sap-integration.md](../architecture/sap-integration.md). |

Diese Reihenfolge ist keine Priorisierung, sondern grob an der Reihenfolge im [Implementierungsplan](../architecture/implementation-plan.md) orientiert. Wir formalisieren jede Entscheidung als eigenes ADR, sobald die zugehörige Phase ansteht – inklusive Alternativen, die wir verworfen haben, und den jeweiligen Trade-offs.
